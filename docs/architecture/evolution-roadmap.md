# NorthLedger 企业级演进路线

演进原则：先把现有 Java、MySQL、React、Docker、Kubernetes 和可观测性用深，再考虑新增组件。路线中的候选项不是当前技术栈，也不能写入简历“已完成”；任何新增技术都应先说明它解决的真实问题、学习成本和替代方案，经确认后再实施。

## 当前版本：业务、安全与运维闭环

- 账户、幂等转账、双录流水和运行读模型。
- 用户、角色、BCrypt、MySQL 共享会话、CSRF 和安全审计。
- Docker Compose 完整运行环境与非 root 镜像。
- Prometheus、Grafana、Alertmanager、Loki 和 Alloy。
- Linux systemd/Nginx 发布、回滚、巡检、日志轮转和备份恢复。
- Kubernetes/Helm 双副本、探针、资源限制、HPA、PDB、RBAC、NetworkPolicy 和 PVC 实践。
- GitHub Actions 后端测试、前端安全门禁、Helm 校验和镜像构建。

完成标准：能够独立启动、执行业务、解释权限、发现故障、定位原因、恢复服务并留下证据。

## 下一阶段优先做深，不新增技术栈

1. 亲自复现三类角色权限和安全审计。
2. 设计并执行并发转账、余额不足、重复请求和数据库中断测试。
3. 建立有依据的业务/可用性 SLI 与告警阈值，减少无意义告警。
4. 在三节点实验集群复现节点不可用、Pod 重调度、发布失败和回滚。
5. 定期执行备份恢复演练并记录 RPO、RTO 和恢复校验结果。
6. 为每个真实故障补充时间线、根因、恢复动作和防复发措施。

## 只有满足触发条件才讨论的候选项

| 候选能力 | 触发条件 | 加入前必须回答 |
| --- | --- | --- |
| Redis | 数据库重复读形成可量化瓶颈 | 缓存什么、多久过期、如何防止脏数据 |
| 消息队列/Outbox | 交易后需要可靠通知其他系统 | 如何保证事务消息、重复消费和失败补偿 |
| OpenTelemetry tracing | 出现跨进程调用且日志/指标无法定位 | 采样率、存储成本和 trace 与日志如何关联 |
| 自动化主机配置工具 | 需要重复管理多台 Linux 主机 | 当前脚本的重复成本是否已经超过引入成本 |
| 服务拆分 | 模块需要独立发布、扩缩容或团队负责 | 分布式事务、接口兼容和运维成本如何处理 |

Milvus、Service Mesh、多集群、复杂 Operator 和大规模高可用中间件没有当前业务需求，不进入默认路线。
