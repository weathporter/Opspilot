# Kubernetes 故障记录（两节点主线，三节点可复用）

本目录存放**实际观察过**的 NorthLedger Kubernetes 故障，而不是为了简历预先编造的案例。每个事件复制 `template.md` 后单独建文件；没有在真实集群执行的演练只留在 Runbook 中，不在这里写“已恢复”。

## 写之前先区分四类话

1. **现象**：操作者或用户看到了什么，例如 `READY 1/2`、浏览器 503、Prometheus Target `DOWN`。必须有时间和原始证据。
2. **事实**：命令、Events、日志、指标实际显示什么；尽量保存脱敏原文，不凭印象重写。
3. **推断**：根据事实怀疑什么，必须写明尚待验证，不能把时间上同时发生的两件事直接写成因果。
4. **结论**：通过有针对性的验证排除了其他解释，并在修复后通过复测。若没有足够证据，写“根因未确认”。

一份好记录能回答面试官的追问：**为什么先看这条命令？它的输出排除了什么？你做的动作是否可能伤害数据？用什么证明用户侧恢复？**

## 证据安全

- 不提交 kubeconfig、Secret 的 YAML/明文、密码、Token、Cookie、完整用户信息或数据库备份。
- 节点 IP、主机名和时间可以按公开仓库要求脱敏，但保留节点间关系；不要把关键错误行删掉。
- 截图必须覆盖命令、输出、时间和对象名；仅一张 `Running` 截图不能证明业务恢复。
- 先记录原始证据再修复；如果紧急处理不能等待，至少在时间线写明当时观察到的事实和动作。

## 可复述结构

`发现异常 → 确认影响面 → 收集状态/Events/日志/指标 → 提出并验证假设 → 选择最小恢复动作 → 业务复测 → 复盘预防`
